# Восстановление публикаций — v0.35

> Справка отдельного этапа. Версии и результаты проверок ниже относятся к моменту его разработки. Текущие настройки — в [README](../README.md) и [развёртывании](deployment-current.md), подтверждённые результаты — в [готовности пилота](pilot-readiness.md).

## Что изменилось

Новые файловые публикации из общей библиотеки, формы управления материалами дисциплины и помощника проходят через общий протокол. До первого серверного запроса браузер сохраняет идентификатор попытки, подтверждённые поля, имя, размер, MIME и SHA-256 файла. Повтор с теми же полями и содержимым использует тот же идентификатор. Изменённый документ или назначение не заменяет незавершённую попытку. Серверное резервирование и завершение идемпотентны.

Одна незавершённая попытка сохраняется на аккаунт и режим в этом браузере. Современные браузеры с Web Locks также исключают параллельную обработку этой записи в разных вкладках. На другом устройстве локальной записи нет; серверные ограничения резервирования всё равно действуют. Данные для повтора не переносятся между аккаунтами и демонстрационным/рабочим режимом. Файл в localStorage не записывается.

После ошибки можно повторить обычную загрузку с теми же полями или открыть «Добавить документ с ИИ». Помощник покажет незавершённую публикацию независимо от текущей дисциплины. После перезагрузки нужно выбрать тот же файл; совпадение имени недостаточно — проверяется хеш содержимого. Без исходного файла доступны проверка результата и отмена. Незавершённые попытки, созданные старыми версиями без локальной записи, удаляются существующими кнопками управления материалами/библиотекой.

После потери ответа Storage клиент сначала пытается подтвердить уже загруженный объект. После потери ответа о публикации повторное резервирование возвращает прежний результат. Подтверждённая публикация очищает локальную запись. Ошибка последующего обновления списка не превращается в новую загрузку. Если браузер запрещает сохранение записи до начала новой загрузки, публикация блокируется с объяснением — серверный резерв ещё не создаётся. Очистка данных сайта удаляет локальную запись; незавершённый серверный резерв может потребовать удаления через управление.

## Безопасная отмена

SQL v0.35 добавляет проверку состояния и отмену. Эти вызовы доступны только вошедшему активному пользователю для его собственной попытки. Новая отмена требует прав публикации; удаление существующего файла проходит прежние проверки управления материалом. При изменении прав может понадобиться помощь владельца через обычное управление файлами.

Отмена сериализована с резервированием и завершением загрузки. Уже опубликованная попытка возвращает результат и ничего не удаляет. Незавершённая переводится в удаление; после этого завершить её публикацию нельзя. Файл удаляется через Storage API, и только после подтверждённого отсутствия объекта удаляются резервирующие строки. Обрыв удаления оставляет состояние для повторной отмены. Закрытие/перезагрузка не превращает такую попытку обратно в загрузку. Отмена до резервирования оставляет серверную отметку, чтобы запоздалый запрос не начал публикацию заново.

Незавершённый материал остаётся скрыт от студента существующими правами. Исходный файл задания продолжает защищаться от обычного удаления после публикации.

## ИИ и бесплатный тариф

Анализ необязателен. Пользователь может сразу заполнить тип, название и дисциплину вручную. Согласие на передачу Gemini требуется только для анализа. Отсутствующий ключ, исчерпание квоты или ошибка анализа не блокируют ручную публикацию. ИИ не назначает срок и баллы и не публикует без утверждения. Повтор, проверка состояния и отмена не вызывают Gemini. Прежние дневные/минутные ограничения и кеш остаются в силе.

## Установка

Если в базе нет `public.material_intakes` или предыдущие обновления пропущены, выполните **один** полный файл `supabase/StudyHub_upgrade_to_v0.35.sql`. Он обновляет существующую базу StudyHub с базовыми миграциями 001–010, работает одной транзакцией и допускает повторный запуск. Если выбрана другая/пустая база, предварительная проверка остановит выполнение без изменений. Отдельные обновления после него выполнять не нужно.

После установленной базы v0.31 также можно выполнить небольшой файл `supabase/StudyHub_update_v0.35.sql` в Supabase SQL Editor. Он не содержит ключей и допускает повторный запуск. Новая миграция для последовательной установки: `supabase/migrations/202610160021_upload_recovery.sql`. Затем опубликуйте фронтенд v0.35.

Без этого SQL безопасный повтор на прежнем протоколе работает, а проверка состояния и отмена объясняют необходимость обновления. Если сервер подтвердил отсутствие функции отмены, интерфейс сохраняет возможность повторить исходную загрузку. Автоматически SQL в живом проекте не применён: в текущей среде нет административного подключения к базе или токена управления Supabase. Публичный anon key не позволяет выполнять миграции. Ключ Gemini для этих улучшений не нужен.

## Проверки

- `npm test`: прежние контракты, новый SQL, повторное применение обновления, изоляция аккаунтов, оригинал файла, восстановление формы, потерянный ответ и повтор отмены.
- `npm run test:upload:recovery:browser`: dev-сервер порта 5266 или `UPLOAD_RECOVERY_TEST_URL`; имитация обрывов, перезагрузка, ручная публикация без Gemini, чтение студентом и мобильный экран.
- `npm run test:material:intake:browser`: согласие, распознавание, утверждение, категории, права старосты/преподавателя и исходный файл задания.
- `tests/upload-intake.test.ts`: транспортный протокол с потерей ответов до/после фактической записи.
- SQL проверяется локально в PGlite с RLS; браузерные обрывы воспроизводятся в деморежиме. Это не проверка подключения к живому Storage или реального запроса Gemini.
