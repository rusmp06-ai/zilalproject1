# Серверная модель доступа — этап 2

## Что реализовано в SQL

- Студент создаёт только свой профиль; поля blocked и роль владельца не доступны для записи.
- Владелец выдаёт приглашение старосте. Одно принятое приглашение даёт право создать одну группу. Это предварительный лимит, который владелец может расширять новыми приглашениями.
- Староста создаёт дисциплины и приглашения только своей активной группы.
- Преподаватель принимает одноразовый секретный токен с назначенными дисциплинами. Повторный вызов не расходует квоту и не дублирует назначение. Истёкшие/отозванные ссылки не работают.
- Ссылка перестаёт работать, если её автор заблокирован или лишился соответствующих полномочий.
- Владелец блокирует аккаунт/группу и создаёт/снимает ограничения разделов.
- Все реализованные изменения через RPC записываются в аудит в той же транзакции.
- Данные групп изолированы RLS. Преподаватель видит только назначенные курсы. Библиотека общая; запрет любой активной группы пользователя закрывает библиотеку для пользователя.
- Токены приглашений хранятся только как SHA-256. Исходная ссылка возвращается создателю один раз.

## Важные ограничения

Миграции применены и сценарии проверены в PGlite (PostgreSQL с имитацией auth.uid()). SQL нужно дополнительно проверить в новом Supabase-проекте. Настоящий Supabase здесь не подключён. Членства и ограничения не меняются напрямую из браузера; работа ведётся через проверенные функции.
Повышенные роли выдаются только по секретной ссылке. Без подтверждения email такая ссылка является доказательством приглашения, поэтому её нужно передавать преподавателю лично. Привязка к неподтверждённому email сама по себе не защищает ссылку. Email-привязка из раннего предложения пока не реализована.
Владелец создаётся доверенной ручной SQL-операцией: сначала аккаунт и профиль, затем запись в platform_owners по UUID. Клиент не может назначить себя владельцем.
Блокировка прекращает новые защищённые запросы; уже загруженные данные не исчезают. Она не удаляет сессию Auth, но закрывает доступ к учебным данным.

Приватные файлы и библиотека добавлены в v0.4, дисциплины в v0.5, задания и оценки в v0.6, расписание и объявления в v0.7. Интерфейс и Supabase-адаптер реализованы, но настоящий проект Supabase ещё не подключён. Перенос студентов, отзыв ссылок и снятие назначения дисциплины добавлены в v0.10. Остались смена ролей, дополнительные личные инструменты и ИИ. Доступ к файлам защищён политиками приватных bucket; сырые приглашения клиенту не выдаются.

## Основные RPC

| RPC | Кто вызывает | Действие |
|---|---|---|
| create_invitation | Владелец / староста своей группы | Возвращает секретный токен |
| redeem_invitation | Активный пользователь | Принимает приглашение атомарно |
| create_group | Владелец / обладатель приглашения старосты | Создаёт группу и членство старосты |
| create_course | Владелец / староста своей группы | Создаёт дисциплину |
| signup_groups | Любой | Минимальный список доступных групп для регистрации |
| join_group / request_group_access | Активный пользователь | Отправляет заявку, не выдаёт членство |
| set_block | Владелец | Блокирует/разблокирует аккаунт или группу |
| deny_section / remove_denial | Владелец | Управляет запретами |
| revoke_invitation | Владелец / автор-староста | Отключает ссылку |

## Следующий этап

Проверить миграции, Auth, Storage и сценарии в настоящем Supabase. Подтверждение email поддерживается; настройте Site URL и разрешённые Redirect URLs. Секретный service_role не используется в клиенте.

Студент выбирает одну активную группу. Самостоятельное переключение группы существующим участником закрыто, чтобы не обходить ограничения группы. Перенос владельцем добавлен в v0.10; подробности в [access-management.md](access-management.md).

Расписание и объявления: матрица прав и RPC описаны в [group-board.md](group-board.md).
