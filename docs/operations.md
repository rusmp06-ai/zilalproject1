# Эксплуатация StudyHub

Этот документ описывает выпуск, диагностику и восстановление. Наличие инструкции не означает, что живая резервная копия уже создана или испытана.

## Выпуск и проверка сайта

1. Пройти `npm run verify`. Он проверяет приложение, SQL, единый файл edge-функции, браузер и офлайн-режим.
2. CI для main сохраняет **studyhub-site** — обычную production-сборку для Cloudflare Pages/Netlify, только если в GitHub repository variables заданы публичные VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY. Без них артефакт рабочего сайта не выпускается; сборки для тестов используют пустые значения. **studyhub-demo** — отдельная демонстрация без Supabase, не рабочий сайт.
3. Публиковать весь каталог `dist/`, включая `build-info.json`, `_headers`, `sw.js` и `assets/`. Не публиковать исходники, `.env` или `node_modules`.
4. После публикации задать `STUDYHUB_SITE_URL` в среде и запустить `npm run test:deployment`. Он проверяет HTTPS, стартовый JS, версию/коммит, настройки email, существующий тестовый аккаунт, CORS и политику ИИ. Код 2 означает, что есть непройденный или заблокированный пункт.
5. `npm run test:deployment -- --ai` дополнительно отправляет **один синтетический документ** в развёрнутую edge-функцию. Он не публикует материал и не отправляет пользовательские файлы. Google может учитывать такой запрос. Обычная проверка его не делает.

Проверка использует существующие VITE_SUPABASE_URL/ANON_KEY и отдельные STUDYHUB_TEST_EMAIL/PASSWORD из защищённой среды. Они не попадают в отчёт. Сессия проверки закрывается с `scope=local`, не завершая другие входы пользователя. Отчёт: `test-results/deployment.json`.

`build-info.json` не содержит ключей. Коммит указан только для чистого Git checkout; при сборке ZIP без .git или при изменённых исходниках он равен null. Это не доказательство совпадения коммита; проверяющий скрипт не подменяет такую проверку совпадением версии.

## Развёртывание ИИ через браузер

Для Supabase Editor подготовлен [StudyHub_material_analyze.js](../supabase/StudyHub_material_analyze.js). Это один автоматически собранный файл из `supabase/functions/material-analyze/`; сторонние пакеты закреплены npm-версиями. В нём нет ключей. `npm run edge:generate` обновляет файл, `edge:check` и Deno проверяют его соответствие исходникам и запуск.

1. В нужном проекте Supabase открыть Edge Functions и создать функцию **material-analyze** через редактор.
2. Заменить содержимое index.ts содержимым подготовленного JS-файла и развернуть. JavaScript этого файла допустим внутри index.ts.
3. В secrets функции задать GEMINI_API_KEY и ALLOWED_ORIGINS — точный основной HTTPS-адрес сайта без завершающего слеша. SUPABASE_URL, SUPABASE_ANON_KEY и SUPABASE_SERVICE_ROLE_KEY предоставляет среда функции. Не переносить service_role в frontend и не присылать ключи в чат.
4. Оставить проверку JWT включённой; сервер дополнительно проверяет пользователя и право публикации. Если платформа использует новый формат ключей и требует иной настройки шлюза, сверить официальную инструкцию Supabase, сохранив серверную проверку пользователя.
5. Повторить `npm run test:deployment -- --ai` и анализ синтетического материала через сайт. Серверный запрос без Origin не доказывает, что браузерный CORS настроен верно.

Для CLI остаётся исходная папка функции и команда `supabase functions deploy material-analyze --project-ref YOUR_PROJECT_REF`. В этой среде административная авторизация Supabase не предоставлена; один файл подготовлен для конкретного действия владельца.

## Ошибки и восстановление интерфейса

Если стартовый JS не скачался, вместо пустого экрана остаётся экран загрузки с повтором. Ошибку React в разделе или приложении перехватывает экран восстановления. Обновление страницы не удаляет локальные черновики, закладки или сохранённые файлы.

«Скачать отчёт об ошибке» создаёт локальный JSON: версия, время, тип ошибки, название раздела, состояние сети и число повторов. Нет текста ошибки/документа, account ID, email, пути файла, URL, JWT и пароля. Максимум 30 записей. Повреждённые значения localStorage фильтруются перед экспортом; недоступное хранилище не мешает обработке ошибки.

Это **локальная диагностика**, не центральный сбор ошибок со всех устройств. Никакие отчёты автоматически наружу не отправляются. Владелец может получить файл от участника пилота и сопоставить время с журналами Supabase Auth/API/Storage/Functions. Не добавлять содержимое пользовательских документов в журнал задач.

## Резервирование до допуска реальных работ

Цели для пилота: копия не реже раза в сутки и перед изменением схемы; целевое восстановление — четыре часа. Это цели, а не измеренный SLA. Автоматическая копия и пробное восстановление пока не подтверждены административным доступом.

Полная копия состоит из:

- схемы, ролей и данных приложения, а также нужных данных Auth и метаданных Storage;
- **байтов всех файлов** приватных бакетов studyhub-library, studyhub-courses и studyhub-submissions;
- исходников функций и точного Git-коммита; серверные secrets сохраняются отдельно в защищённом хранилище.

Дамп таблиц storage.objects не содержит байтов PDF, лекций и работ. Копия только public не восстанавливает учётные записи. Сохранённые файлы браузера и GitHub не являются резервной копией живой базы.

Порядок для оператора с правами Supabase:

1. Проверить проект, инвентаризацию бакетов и доступный способ резервирования тарифа. Создать закрытый каталог вне Git; backups/ исключён из репозитория.
2. Штатным Supabase CLI экспортировать роли, схему и данные. Наличие флагов `db dump --role-only`, `--data-only`, `--use-copy`, `--schema`, `--linked`, `--file` проверено по CLI 2.121.0. Экспорт и импорт живого проекта из этой среды **не выполнялись**. Включение управляемых схем Auth/Storage и порядок восстановления сверить с инструкцией текущего Supabase: это не обычная миграция public.
3. Отдельно скопировать содержимое каждого бакета. CLI 2.121.0 поддерживает `storage cp --recursive --linked`; проверить список объектов, число файлов и контрольные суммы, не ограничиваться успешным кодом команды.
4. Хранить копию за пределами самого Supabase-проекта, ограничить доступ, защищать персональные данные. Записать дату, проект, Git-коммит, размеры и SHA-256 архивов.
5. Восстановить в **отдельный пустой тестовый проект**, не поверх рабочей базы. Создать/проверить бакеты, восстановить данные и байты файлов, настроить Auth и secrets функций. Не запускать накопительный upgrade поверх восстановленной схемы без сверки истории миграций.
6. Подтвердить вход, роли и отказ чужому пользователю; скачать реальные байты материала и работы; проверить заметки, расписание, сдачу и оценку. Сопоставить число строк/объектов и записать фактическое время восстановления.

Пока нет этой записи, считать восстановление неподтверждённым. Документация: https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore . Открытие документа из этой среды ограничено сетевым доступом; команды не выдаются за выполненную живую копию.

## Выпуск и откат

Перед выпуском записать текущий коммит, backup и результаты тестов. Frontend можно вернуть на предыдущий проверенный артефакт хостинга. SQL не откатывают вслепую: уже записанные работы и данные сохраняются, исправление обычно выпускают новой совместимой миграцией. Ошибка frontend сама по себе не является поводом удалять базу или повторять все SQL.
