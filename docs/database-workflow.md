# Процесс базы данных

## Один источник

Менять SQL можно только новой последовательной миграцией в `supabase/migrations/`. Уже выпущенные миграции не редактируются. После изменения:

```sh
npm run sql:generate
npm run sql:check
npm test
```

`scripts/sql-bundles.mjs` хранит только диапазоны выпусков, не определения функций. Он собирает совместимые исторические патчи и `StudyHub_upgrade_latest.sql` из исходных миграций с SHA-256 каждого файла. CI сравнивает точный результат генерации, затем сравнивает таблицы/колонки, ограничения, индексы, триггеры, RLS, ACL и определения функций двух путей установки. PGlite предоставляет UUID/SHA256 сам; расширение pgcrypto исключено только из тестовой установки.

## Новый проект

Основной путь — последовательные миграции через Supabase CLI. После установки официального CLI выполните `supabase init`, если config.toml ещё не создан, затем привяжите **нужный** проект и проверьте список и dry run:

```sh
supabase link --project-ref YOUR_PROJECT_REF
supabase migration list
supabase db push --dry-run
```

Применение `supabase db push` выполняется только после проверки выбранного проекта и списка операций. Пароли передаются штатным способом CLI, не в чат и не в Git. Пустую базу нельзя обновлять файлом `StudyHub_upgrade_latest.sql`: он ожидает базу с миграциями 001–010.

## Существующая база с ручными обновлениями

Для уже работающей StudyHub с базовыми миграциями 001–010 скачиваемый `supabase/StudyHub_upgrade_latest.sql` остаётся доступным для SQL Editor. Весь файл выполняется одной транзакцией, повторный запуск проверяется тестами с сохранением существующих записей. Старые URL `StudyHub_update_v*.sql` сохранены для совместимости; это автоматически созданные файлы, а не второй источник SQL.

**SQL Editor не записывает историю Supabase CLI.** Перед первым `db push` к такой базе необходимо сверить `supabase_migrations.schema_migrations` и фактическую схему. Если история отсутствует или неполна, нельзя просто отметить все версии выполненными или запустить push: сначала подтверждают, какие миграции действительно представлены в базе, затем выполняют адресный `migration repair`. Автоматическая правка истории живого проекта в этой работе не выполняется.

## Обновление схемы

1. Добавить миграцию, не переписывая выпущенную.
2. Генерировать SQL и проверить совпадение схемы обоих путей.
3. Проверить обновление тестовой базы и существующие данные.
4. Сделать резервную копию перед изменением живой базы.
5. Применить штатным путём, принятым для этого проекта; записать версию и результат в журнал развёртывания.

Текущий выпуск сопровождения не добавляет миграций и не требует повторять ранее выполненный SQL ради форматирования, CI или CORS.
